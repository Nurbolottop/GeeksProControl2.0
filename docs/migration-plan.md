# План финальной миграции 1.0 → 2.0

> **Не выполнять без отдельного письменного разрешения руководителя.**
> До этого 1.0 — единственный источник рабочих данных, а 2.0 работает на
> собственной базе с синтетическими данными (stage). При деплое 2.0 данные
> 1.0 автоматически не переносятся: ни entrypoint, ни compose их не читают.

## Последовательность внедрения

1. Разработка
2. Тестовый деплой 2.0 (stage, синтетические данные)
3. Завершение разработки
4. **Проверка миграции** — репетиции на копии, раздел 2
5. **Перенос актуальных данных** — разделы 3–4
6. Подключение действующих стажёров к Telegram-боту
7. Настройка Telegram-групп и тем по проектам
8. Полноценный запуск

## 0. Неизменные правила

- 2.0 никогда не подключается к базе 1.0 и не монтирует её тома. Данные передаются только файлом дампа.
- С базой 1.0 выполняются только операции чтения (`pg_dump`). Миграции, правки и очистка в ней запрещены.
- После переноса база 1.0 остаётся защищённым резервом и автоматически не удаляется (раздел 6).
- История миграций 2.0 — надмножество истории 1.0: миграции, существующие в 1.0, не удаляются, не переименовываются и не схлопываются. Только так дамп 1.0 доводится до схемы 2.0 обычным `migrate`.

## 2. Репетиция (повторяемая, без влияния на 1.0 и stage)

1. Дамп 1.0 только на чтение. `pg_dump` берёт согласованный снимок и не блокирует работу 1.0:
   ```bash
   cd /root/GeeksProControl
   docker compose -p geekspro -f docker-compose.prod.yml exec -T db \
     sh -c 'pg_dump -U "$POSTGRES_USER" -Fc "$POSTGRES_DB"' > /root/backups/gp1-rehearsal-$(date +%F-%H%M).dump
   sha256sum /root/backups/gp1-rehearsal-*.dump
   ```
2. Восстановление в **отдельную одноразовую** базу: отдельный compose-проект
   `geekspro2-rehearsal`, без web-порта и без бота, `TELEGRAM_OUTBOUND_MODE=off`,
   без Google-ключа. Это не stage-база и не база 1.0.
3. Применить к ней `migrate` кода 2.0. Записать время и предупреждения.
4. Сверка (раздел 5): количество записей, целостность, контрольные выборки.
5. Удалить репетиционную базу и дамп: в них реальные персональные данные.

## 3. Перенос (день X)

**3.1. Резервные копии до начала:**
- финальный `pg_dump -Fc` базы 1.0 → `/root/backups/gp1-final-<дата>.dump` и копия вне сервера; права 600, контрольная сумма;
- архив media 1.0 (`/root/GeeksProControl/app/media`) + манифест `sha256` всех файлов;
- копии `.env` и nginx-конфига 1.0 (только чтение, для отката);
- проверка: дамп восстанавливается в одноразовую базу без ошибок.

**3.2. Заморозка изменений в 1.0.** Изменения во время переноса исключаются, а не догоняются:
после заморозки в 1.0 никто ничего не пишет, поэтому финальный дамп полный и дельта равна нулю.
- Остановить (`stop`, **не** `down`, без `-v`) сервисы 1.0, которые пишут данные:
  web (сотрудники и публичные формы), celery, celery-beat, graduate_bot. Контейнер БД 1.0 продолжает работать.
- На время окна nginx 1.0 показывает страницу «идут технические работы». Изменение конфига
  1.0 допускается только в этот момент и только с разрешением; перед reload — `nginx -t`.
- Зафиксировать время заморозки.

**3.3. Финальный дамп и восстановление:**
1. Финальный `pg_dump` 1.0 после заморозки и его контрольная сумма.
2. Пустая production-база 2.0 (stage-база с синтетикой удаляется или заменяется; в production её данные не попадают).
3. `pg_restore --no-owner --role=<пользователь 2.0>` в базу 2.0.
4. `migrate` кодом 2.0.
5. Media: `rsync -a --checksum` в `/opt/geekspro2/storage/media`, `chown 10001:10001`.
6. Сверка (раздел 5). Любое расхождение — откат (раздел 7).

## 4. Переключение пользователей

1. Production-`.env` 2.0: `GP2_ENVIRONMENT=production`, свои `SECRET_KEY` и пароли.
   Хеши токена бота и таблицы 1.0 убираются из `PROTECTED_VALUE_HASHES` **только здесь**,
   потому что ресурсы 1.0 переходят в 2.0.
2. Домен: основной адрес — `gpro.zeastudio.su`; `geekspro.zeastudio.su` отвечает 301-редиректом
   на тот же путь в 2.0, поэтому старые ссылки (брифы, анкеты по токенам) продолжают работать.
   Basic Auth со stage снимается.
3. Пользователи входят заново (другие имена cookies); пароли сохраняются, хеши переехали вместе с базой.
4. **Telegram-бот** (этап 6): бот 1.0 уже остановлен; его токен переносится в 2.0
   (одновременно polling ведёт только один процесс), сначала `TELEGRAM_OUTBOUND_MODE=allowlist`
   на себя, после проверки — `on`. Стажёры продолжают в том же боте: `telegram_chat_id`,
   статусы и выбор уже в базе, повторная регистрация не нужна.
5. **Группы и темы** (этап 7) — отдельным шагом после стабильной работы бота.
6. Google Sheets: ключ и таблица 1.0 подключаются к 2.0 только после сверки.

## 5. Сверка целостности

Отчёт сравнивает 1.0 (по финальному дампу) и 2.0 (после `migrate`):

| Проверка | Как |
|---|---|
| Количество записей | `SELECT count(*)` по каждой таблице 1.0; в 2.0 те же таблицы — те же числа, новые таблицы 2.0 перечисляются отдельно |
| Ключевые срезы | пользователи по ролям, стажёры по статусам, проекты по статусам, участники команд, документы, резерв, собрания и отметки посещаемости |
| Telegram | число стажёров с `telegram_chat_id` совпадает |
| Целостность | внешние ключи без «сирот», `ANALYZE` без ошибок, sequence ≥ max(id) по каждой таблице |
| Миграции | список `django_migrations` 1.0 целиком присутствует в 2.0; новых миграций 2.0 ровно столько, сколько ожидалось |
| Media | количество файлов и sha256 по манифесту; все пути из `FileField` существуют |
| Функциональная проверка | вход руководителя, PM, тимлида; открытие 10 случайных проектов, стажёров и документов; публичная ссылка брифа |

Отчёт сохраняется вместе с дампом. Подпись ответственного — условие переключения.

### 5.1. Команда сверки (этап 10B)

`manage.py migration_report` — только чтение своей базы, без персональных данных:

```bash
# на репетиционной базе: до migrate (дамп 1.0) и после migrate кодом 2.0
python manage.py migration_report --media --output /root/backups/report-before.json
python manage.py migrate
python manage.py migration_report --media --output /root/backups/report-after.json
python manage.py migration_report --compare /root/backups/report-before.json /root/backups/report-after.json
```

`--compare` завершается ошибкой при любом расхождении — переключение запрещено.

**Контрольные показатели:** пользователи по ролям; стажёры по статусам и статусам
выпускника; выпускники (вычисленные); проекты по статусам; заказчики; участники команд
по статусам и ролям; документы; заявки (заморозка, возвращение, отмена, повторная,
выход); периоды стажировки; предупреждения; журнал аудита (кадровые события);
недельные / месячные отчёты 1.0 и отчёты по проектам; оценки по 7 критериям и баллы
WorkScore; собрания табеля и отметки посещаемости; резерв; задачи по статусам;
стажёры с Telegram; список `django_migrations`; sha256 каждого файла из `FileField`
и отсутствующие файлы; sequence ≥ max(id).

**Риски связи профилей (должны быть пустыми):** дубли `telegram_chat_id` (бот привязывает
человека по chat id — дубль = чужой профиль), группы дублей телефона (сверка продаж и
«Я уже стажёр» уйдут на ручную сверку), больше одного открытого периода стажировки.

### 5.2. Аудит цепочки миграций (этап 10B)

* Все 84 миграции 1.0 присутствуют в 2.0 побайтно одинаковыми; новых миграций 2.0 — 23.
* Новые миграции только добавляют: CreateModel / AddField / AddConstraint, AlterField —
  только списки значений (choices) и разрешение пустого значения; сужения длины, снятия
  NULL, удаления полей и таблиц нет. Разрушающие операции в истории — только унаследованные
  из 1.0 (уже применены в базе 1.0).
* Миграции данных 2.0: `tasks.0003_legacy_assignee` — переносит прежнего исполнителя
  задачи в `TaskAssignment`, ничего не меняя в задаче (добавляет записи; обратная — noop).
* Поля, требующие сверки после переноса: `Intern.branch` / `city` (Бишкек/Ош — нужно для
  продаж), `Intern.specialization` (направление), `Intern.telegram_chat_id` (дубли),
  телефоны (формат и дубли), `TeamMember.left_reason` старых записей (влияет на выпуск),
  `Internship` (открытые периоды), `Task.assignee` → `TaskAssignment` (количество).
* Документы: файлы media 1.0 переносятся `rsync --checksum`; манифест `--media` до и после
  обязан совпасть; пути `FileField` без файла — блокер.

## 6. Сохранение 1.0 как резерва

- Контейнеры 1.0 остановлены (`stop`), а не удалены; том `geekspro_postgres_data`, каталог
  `/root/GeeksProControl`, его `.env` и Git-репозиторий 1.0 не трогаются.
- Финальный дамп и архив media 1.0 хранятся на сервере (права 600) и вне сервера, с контрольными суммами.
- На этом сервере запрещены `docker volume prune`, `docker system prune --volumes` и
  `docker compose down -v` в каталоге 1.0: они удалят базу 1.0, а на сервере есть и другие проекты.
- Удаление резерва 1.0 — только отдельным решением руководителя, не раньше согласованного срока.

## 7. Откат

| Когда | Действие | Потери |
|---|---|---|
| До переключения (сверка не прошла, ошибка восстановления) | остановить 2.0, вернуть nginx 1.0, `start` сервисов 1.0 | нет: 1.0 заморожена, её база не менялась |
| После переключения, до точки невозврата (рекомендуется 48 часов) | то же + в 1.0 вручную вносятся изменения, сделанные в 2.0 (их список — из журнала `audit` 2.0) | только ручной перенос свежих правок |
| Бот | остановить бота 2.0, затем запустить бота 1.0 (одновременно — никогда) | нет |

Обратной миграции схемы 2.0 → 1.0 нет и не будет. Поэтому откат — это всегда возврат к
нетронутой базе 1.0, а не перенос данных обратно. После точки невозврата 2.0 становится
единственной системой, а 1.0 остаётся резервом (раздел 6).

## 9. Две обязательные репетиции на копии реальных данных (⛔ не проведены)

Каждая — на **изолированном** compose-проекте `geekspro2-rehearsal` (своя БД, без бота,
`TELEGRAM_OUTBOUND_MODE=off`, без Google-ключа, без web-порта наружу), с дампом,
полученным **по отдельному разрешению** (раздел 2.1). После — база и дамп удаляются.

```bash
DC="docker compose -p geekspro2-rehearsal -f docker-compose.prod.yml" \
  scripts/migration-rehearsal.sh --dump /root/backups/gp1-rehearsal-<дата>.dump /root/rehearsal-<N>
```

с количествами по реальным данным, время каждого шага.
**Репетиция 2 — приёмочная:** после решений руководителя по §8.1 (применённых на
копии!), повтор с новым дампом + бизнес-проверки ниже.

Критерии успеха (обе репетиции, все пункты):

| Критерий | Проверка |
|---|---|
| Нет необъяснённой потери записей | `compare.txt`: «Сверка без расхождений»; каждое известное отличие — в протоколе с причиной |
| История сохранена | `audit_events`, `team_members` по статусам, `project_reports`, `weekly_reports_legacy` — до = после |
| Права сохранены | `users` по ролям до = после; вход руководителя, ПМ и тимлида (`scripts/smoke_check.py` на копии) |
| Контрольные показатели совпадают | `migration_report --compare` без ошибок |
| Файлы — только авторизованным | `smoke_check.py` с `GP2_SMOKE_MEDIA`: аноним → вход, чужая роль → 404 |
| Контрольные суммы | `media.sha256` до = после, `missing_by_field` пуст |
| Бизнес-сценарии работают | вход ролей, открытие 10 случайных проектов/стажёров/документов, Kanban, отчёты, Dashboard |
| Ошибки задокументированы | протокол репетиции: время, предупреждения `migrate`, решения по §8.1 |

с ошибкой; `smoke_check` с ошибками; не входит руководитель / ПМ / тимлид; media

## 11. Откат с учётом данных 2.0 (⛔)

| Когда | Действие | Данные 2.0 после T1 |
|---|---|---|
| **A.** До T1 (шаги 4–9) | остановить 2.0; nginx 1.0; `start` сервисов 1.0 | нет — 1.0 заморожена, её база не менялась |
| **B.** После T1 | **сначала** заморозить 2.0 (`stop` web/bot, страница работ); `post_cutover_changes --since <T1> --output delta.json`; руководитель согласует перенос каждой группы записей в 1.0 вручную; только потом — `start` 1.0 и бот 1.0 | выгружены в `delta.json` (права 600); перенос — вручную по согласованию |
| **C.** После точки невозврата (рекомендуется 48 ч) | откат не выполняется; ошибки исправляются в 2.0 | — |

Простое восстановление старой базы 1.0 после T1 **теряет** всё созданное в 2.0
(заявки, задачи, отчёты, оценки, собрания, регистрации из бота) — без шага выгрузки
`post_cutover_changes` откат B запрещён. Telegram: при откате сначала остановить бота
2.0, затем запускать бота 1.0 — одновременно никогда.
