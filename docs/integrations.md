# Интеграции 2.0: архитектурный задел

Документ фиксирует утверждённые решения. Реализация — на следующих этапах.

## Telegram: один проект — одна группа

**Сценарий.** Руководитель вручную создаёт группу (супергруппу с темами) и
добавляет бота администратором с правом `can_manage_topics`. Бот видит
`my_chat_member` и создаёт в Control заявку «группа ожидает подтверждения».
Руководитель в Control выбирает проект и подтверждает. Бот создаёт по теме на
каждое направление проекта (`createForumTopic`), сохраняет их идентификаторы
и дальше шлёт уведомления в нужную тему.

**Модели (предварительно):**

```
ProjectTelegramGroup   project (OneToOne), chat_id (unique), title,
                       status: pending / confirmed / revoked,
                       confirmed_by, confirmed_at, is_forum
ProjectTopic           group (FK), direction (FK → Specialization),
                       message_thread_id, name; unique (group, direction)
```

**Совместимость уже сейчас:**
- вся отправка идёт через `GuardedTeleBot` — появится только `message_thread_id`, защита и режимы `off/allowlist/on` действуют и для групп;
- в тестах и на stage используются только тестовые группы, их chat_id — в `TELEGRAM_TEST_CHAT_IDS`;
- бот один на проект Control; для групп его лучше перевести с polling на webhook (`/telegram/webhook/<секрет>/`, вне Basic Auth), чтобы web и бот не конкурировали за обновления.

## Переход стажёров на бота 2.0 без повторной регистрации

У стажёров в базе уже есть `telegram_chat_id`, выбор и статусы — всё
это переезжает вместе с базой. Повторно регистрироваться и платить не нужно.

**Рекомендуемый путь — бот переходит вместе с системой.** На время разработки
у 2.0 тестовый бот. В момент переключения боевой бот 1.0 останавливается в 1.0,
его токен переносится в production `.env` 2.0 (и его хеш убирается из
`PROTECTED_VALUE_HASHES` именно там), `TELEGRAM_OUTBOUND_MODE=on`. Для стажёров
ничего не меняется: тот же бот, те же чаты, данные уже в базе.

**Если боту 2.0 нужен новый @username:** Telegram не даёт новому боту писать
людям первым. Тогда каждому стажёру выдаётся персональная ссылка
`t.me/<бот2>?start=<одноразовый токен>`, и последней рассылкой её отправляет бот 1.0
или показывает Control. По `/start <токен>` бот 2.0 привязывает chat_id к
существующей записи `Intern`. Анкета и статусы не запрашиваются заново.

## Видеособрания: Jitsi as a Service (8x8 JaaS)

Своего видеосервера нет. Собрание в Control хранит ссылку на комнату внешнего провайдера.

| Возможность | Как |
|---|---|
| Назначение собрания | существующая модель `Meeting` + поля `provider`, `room_name`, `starts_at`, `ends_at` |
| Персональные ссылки | JWT на участника (RS256, ключ JaaS в `secrets/`), имя и роль (модератор — тимлид) в токене; ссылка выдаётся из Control после входа |
| Telegram-уведомления | через `GuardedTeleBot`, в тему направления группы проекта |
| Подключения и отключения | вебхуки JaaS `PARTICIPANT_JOINED` / `PARTICIPANT_LEFT` → `/integrations/jaas/webhook/` (проверка подписи) → модель `MeetingPresence` (участник, вход, выход) |
| Посещаемость | расчёт по сумме интервалов присутствия; порог «был/опоздал/не был» — настройка |
| Ручные корректировки | тимлид правит итог в `attendance`, исходные события сохраняются, правка пишется в `audit` |

На этом этапе сервисы не покупаются и звонки не запускаются. Ключи JaaS —
только через `.env` и `secrets/`.
